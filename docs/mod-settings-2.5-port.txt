Mod Settings source port for Cyberpunk 2077 2.5
=============================================

Target: executable 3.0.88.46235, RED4ext 1.31.0 and the saved shared SDK.
Date: 2026-10-25. This is a source/build/ABI audit and isolated regression
record. No game startup, gameplay, save/load or settings-persistence test was
performed with this build. No game or MO2 files were changed.

The initial port failed native-definition validation in the user's subsequent
startup attempt. The registration defect and corrected package are recorded
in the follow-up at the end of this document; the original checks below did
not establish successful startup.

Local evidence consulted first
------------------------------
.research/mod-settings/startup-analysis.txt and the v0.2.21 source beside it
record the installed-binary investigation. The matching observed RED4ext log
stops while loading mod_settings.dll, after the plugin logged its starting
version and base address. No matching exception context was recorded.

Installed old DLL SHA256:
  6be425177778a3857a392251bbbcd1aab450dda600c1a56b0f4dd4eac9c3a9cc
Audited retail Cyberpunk2077.exe SHA256:
  d36e74c47592e9c656ae250078cb40b2be63c782af5bfbeff2280d43e653fab4

The old plugin registers callbacks at RTTI vtable slots +0xC0 and +0xC8 with a
0x28-byte callback whose handler is at +0x20. Retail copies/destructs callbacks
through +0x40, with 0x48-byte entries. That mismatch is a demonstrated ABI
defect and a concrete explanation of the startup symptom, but the precise
observed faulting instruction is not known. Changing Query's version alone
cannot repair it; the old DLL already declared runtime independence.

The source port uses the current shared SDK callback at both registration
slots, including ArchiveXL's API helper. Query now declares exactly game 2.5
and the current v1 SDK/API. It does not advertise independence from layouts.

Private layout and call audit
----------------------------
All addresses here are executable RVAs, independent of ASLR. The disassembly
used llvm-objdump; nearby exported audio-library labels were not treated as
names of internal game functions. The existing Codeware ScriptBundle audit
was cross-checked with retail code and used for the common script structures.

Script metadata:
  * ScriptData begins with an additional eight bytes. Its classes array is
    +0xD8, rather than +0xD0. The destructor at 0xA7B3A4/0xA7B49C frees maps at
    +0x08/+0x38/+0x68 and arrays from +0x98 onward; the definition collector at
    0xB2C408 walks the class array at +0xD8.
  * ScriptDefinition grew from 0x18 to 0x40. ScriptClass properties are +0x50,
    with functions +0x90 after an additional 0x20 bytes. ScriptProperty's
    parent/default values/runtime attributes/type are +0x48/+0x68/+0x88/+0xB8.
    ValidateProperty at 0x6BF654 and the class/definition walkers substantiate
    the moved fields. The local source includes real offsetof assertions;
    the shared SDK's disabled Clang offset macro is not used as evidence.
  * IType::FromString now takes const CString&, rather than the fork's raw
    buffer. The port passes constructed strings and looks up built-in types
    by name instead of dereferencing the fork's RTTITYPE macro addresses.

Input mappings:
  Hash        RVA        Observed use
  3702071356  0x786F68   GetMappingCollection reads the map at UserMapping+0xA0
  4196866905  0x787238   clears per-collection state at +0x10
  1773342692  0x18C8510  ApplyOverrides reads manager+0x10, then context+0x08
  3298233196  0x27A47A8  original key-filter hook target
  3993832650  0xA7B3A4   script-bundle destructor/release hook target
  2583235069  0xDCC4B0   overridable input identifier hash routine

  All six hashes resolve uniquely in the installed 2.5 address database.
  Resolution alone does not prove a function signature or structure layout.

  The retail context override at 0x7860F4 independently reads the context's
  action map at +0x28, each action's mapping-name array at +0x08, calls
  GetMappingCollection and traverses 0x40-byte mapping elements. It compares
  the overridable identifier at +0x34 and writes the 16-bit key at +0x02. The
  runtime-map rebuild at 0x786AF4 also walks elements with a 0x40-byte stride.
  Upstream's 0x30-byte element and +0x24 identifier were incompatible. The
  source now uses these observed offsets and leaves unneeded fields opaque.
  It delegates rebuilding to the original ApplyOverrides, without writing
  the old, unaudited manager status fields.

Native settings and script bindings:
  The legacy fork has a custom RuntimeSettingsVar that the shared SDK does
  not expose. NativeSettings.hpp keeps a plugin-owned prefix adapted from
  its MIT-licensed b5ea5919 header; it does not replace an SDK header. The
  legacy and shared SDK license texts are identical.

  The userSettingsVar RTTI registration at 0x17D3BCB declares size 0x48.
  Native accessors read its runtime pointer at +0x40, then the runtime name
  at +0x08 (0x278D9A8), group path at +0x10 (0x278D6E8), display name at +0x18
  (0x278D400), description at +0x30 (0x278D3EC), type at +0x40 (0x278D9E4),
  update policy at +0x41 (0x278D9F8), flags at +0x44, and order at +0x48
  (0x278D9BC). Their RTTI string registrations identify these accessors;
  neighboring functions for other settings subtypes are not used as evidence.
  IsVisible at 0x1919BEC checks flag 0x4; IsDisabled at 0x278DE64 checks
  0x800, so the local flag declaration preserves the additional retail bit.
  The RestoreDefault wrapper at 0x278DF10 calls vtable +0x28; HasChange at
  0x278DE40 calls +0x18. The plugin's corresponding virtuals retain those slots.

  Current API adaptations include explicit v1 loader types, DynArray accessors,
  const-correct RedLib methods, native object creation and explicit script
  argument arrays. The custom ConfigVar wrappers keep their runtime pointer
  at +0x40. The legacy inkActionName CName extension reads its private +0x40
  field within the unchanged 0x58-byte class; its menu use remains a game-test
  item. Native build assertions cover the boundary layouts actually read.

Startup and ownership changes
-----------------------------
The plugin-owned Registrar.hpp replaces the upstream cpcmake hook helper. It
resolves addresses during Main(Load), tries each attachment once, rolls back
earlier attachments on failure, and detaches in reverse order. It does not
resolve game addresses from static hook constructors or spin forever on a
failed attachment. The old DllMain singleton/handle call is removed.

The port does not delete legacy scripts or archives from the game during
startup. Disable old copies in the mod manager before testing. The loader
registers both scripts; ArchiveXL registers the neighboring packed archive.

The source also replaces zero-filled allocation of a nontrivial settings
dependency with a constructed value, corrects its value/property substrings,
removes a shared-to-exclusive lock upgrade in native AddVariable processing,
initializes scalar defaults, checks negative enum indices, and builds group
paths dynamically instead of overflowing a fixed buffer. These are source
defects encountered while adapting this path, not proven causes of the
original session failure.

Dependency overlay and packaging
--------------------------------
Only upstream-pinned deps/red_lib is a build dependency. The private SDK,
cpcmake, ArchiveXL, Detours and logging copies are unused. cpcmake was inspected
locally for original packaging/compiler semantics, but is not initialized by
the build. All native code uses clang-cl, lld-link and Microsoft's STL/CRT.

Startup registration follow-up, 2026-10-25
----------------------------------------
The 03:05:39 RED4ext session loads our DLL successfully and compiles scripts,
then reports all seven Mod Settings native classes and inkActionName.ToName
missing. RED4ext's ValidateScripts hook displays that validation failure and
terminates the process. This explains the recorded startup termination; no
access-violation instruction or matching minidump is claimed. See the separate
mod-settings-startup-2026-10-25-forensics.txt record for captured log, object
and PDB evidence.

The installed failing DLL matched the previous workspace build exactly:
  1854538d22dc7dbccd22218ea41c49da98cc60a2c6a67c5830636ec6227e7b6b
The compiler never instantiated RedLib's inline static template registrars:
RTTI_DEFINE_CLASS/RTTI_EXPAND_CLASS only specialized their builders. The old
fixture constructed a registrar manually and therefore bypassed this defect.
Script compilation alone likewise cannot check the game's native registry.

The managed RedLib overlay now takes a retained address of each class or
expansion registrar after its builder specialization, using the technique
already present in Codeware's RedLib. Clang emits their initialization, while
inline identity prevents duplicate registration across translation units.
The upstream dependency and source Gitlinks remain unchanged. The overlay
was exported and reconstructed through scripts/mod_settings.py, which also
updated its checksum; no patch hash was edited manually.

Validation of this correction:
* Actual declaration macros and registrar templates, included in two TUs:
  old overlay exits 42 with "declared RTTI classes and expansions discovered
  exactly once across translation units"; fixed overlay passes. Engine-facing
  probe operations are replaced with counters; discovery is production code.
* A private RED4ext.dll shim loads a copied actual plugin DLL and calls Main
  with fake loader services. The previously installed DLL exits 42 because
  its registration/description queues are empty. The rebuilt DLL queues both

* Release build passed; the DLL now includes all seven RTTI class names and

  2.5 cache. All 90 Python tests passed (16 optional checks skipped); independent
  patch reconstruction, package verification and six unique address matches
