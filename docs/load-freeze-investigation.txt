Cyberpunk 2077 2.5 loading freeze: investigation and fix plan
Investigated 2026-10-24; game file version 3.0.88.46235.

Finding
-------
A concrete self-deadlock exists in ArchiveXL's EntityAttachment extension.
The same unsafe path is present in the checked-out source, the local Release
DLL and the ArchiveXL DLL installed in the active MO2 profile. The game can
hold its attachment-slot lock exclusively while requesting appearance suffixes.
ArchiveXL's inner-sleeves suffix override calls back into FindSlotData, which
tries to acquire that same non-recursive lock for reading on the same thread.
The owner cannot release its exclusive lock until the nested call returns.

This is the strongest explanation for the reported save-loading freeze. Its
reachability and locking mechanism were checked against the installed game
executable, not inferred solely from address hashes or a successful build.
There is no captured thread stack from the reported 15:26 session, so this is
not proof that every reported freeze stopped at this instruction. No game was
launched, modified or playtested during this investigation.

The user reports that only Cyberpunk stops responding; Alt-Tab still works,
and the pointer stops while the game is in the foreground. This is consistent
with a blocked game process but does not identify a particular lock by itself.

Source evidence
---------------
sources/archive-xl/src/App/Extensions/Attachment/Extension.cpp:
  line 40: installs the GetSuffixValue wrapper.
  lines 248-262: for itemsFactoryAppearanceSuffix.Partial, calls IsVisualTagActive
  for AttachmentSlots.Torso and hide_T1part, with no locked-update guard.
  lines 294-303: IsVisualTagActive calls ITransactionSystem::FindSlotData.

sources/red4ext-sdk/include/RED4ext/Scripting/Natives/gameITransactionSystem.hpp:
  line 104: FindSlotData occupies virtual-table byte offset 0x448.

sources/archive-xl/src/App/Extensions/Attachment/Extension.hpp:
  line 47 already declares thread_local s_skipVisualTagCheck, but the local
  source never reads or sets it. Its declaration alone provides no protection.

sources/archive-xl/src/Red/Addresses/Library.hpp and AttachmentSlots.hpp contain
  no LockedUpdate hook. The saved 001 compatibility patch changes the suffix
  argument to const TweakDBID&, but does not add the reentrancy protection.

The GarmentOverride extension also holds its own mutex across some engine calls.
Those sites were examined as leads, but this investigation does not establish
a deadlock involving that mutex. The demonstrated cycle uses the engine's
attachment-slot lock, not GarmentExtension::s_mutex.

Independent binary evidence
---------------------------
Game executable SHA256:
  d36e74c47592e9c656ae250078cb40b2be63c782af5bfbeff2280d43e653fab4
Address-table SHA256:
  eab304f38074145ab5ef53e2aa741576ba00674138761fafff23252005948fd4

IMPORTANT: the JSON's 0001 offsets are relative to .text. Add its code constant
offset 0x1000 to obtain image RVAs. The preferred image base is 0x140000000.
The following addresses are image RVAs, not raw JSON offsets.

1. Hash 2050568765 resolves to .text+0x89AF5C = image RVA 0x89BF5C.
   At 0x89BF74 the function computes slots+0x100; at 0x89BF86 it calls the
   exclusive-lock wrapper at 0x1FFAD60. The wrapper calls 0x22CA300, which
   atomically changes lock state 0 to 0xFF. The lock is released only after
   the inner call at 0x89BF9F returns (release at 0x89BFB3).
2. That inner function, 0x89BFC0, can call 0x89B6F0 at 0x89C261. This reaches
   the transaction-system virtual method at byte offset 0x1E0 (0x89B9E1).
   The table at image RVA 0x30DC058 maps that slot to 0x89BB50.
3. 0x89BB50 calls 0x757828 at 0x89BBCF; that thunk calls GetSuffixes at
   0x756808 (hash 63057648). GetSuffixes calls GetSuffixValue at 0x219EB00
   at instruction 0x756AA9. The latter is hash 3294244838, hooked by ArchiveXL.
4. The installed ArchiveXL suffix hook starts at DLL RVA 0x4C850. It checks
   the suffix TweakDBID (CRC 0x167F263B, length 0x24) and directly calls its
   visual-tag helper at 0x4D210, with no guard before the call.
   At DLL RVA 0x4D26A the helper calls transaction-system vtable slot 0x448.
5. That slot in the same game vtable maps to FindSlotData, image RVA 0x75A4E0
   (hash 3681039489). It resolves the owner's attachment slots, computes
   slots+0x100 at 0x75A50B, and calls the shared-lock wrapper at 0x75A517.
   The wrapper at 0x1FFADA0 calls 0x22CA420. That reader-lock routine rejects
   0xFF and retries: the current thread is waiting for its own exclusive lock.

Resulting cycle:
  exclusive slot lock -> appearance suffix -> ArchiveXL visual-tag query
  -> FindSlotData -> shared acquisition of the same slot lock -> never returns

The local Release PDB identifies OnGetSuffixValue at DLL RVA 0x4C890 and
IsVisualTagActive at 0x4D250. Disassembly shows the same unguarded path.

Revised implementation plan
---------------------------
See docs/load-freeze-change-plan.txt for the current change sequence. Follow-up
binary/source research superseded the initial single-hook containment proposal:

* Three verified exclusive-lock paths can reach the suffix override, not only
  the published LockedUpdate wrapper.
* The retail engine exposes a non-locking slot lookup at vtable offset 0x450
  and uses it in its own Partial suffix implementation.
* The shared SDK's listener registration and visual-tag methods have incorrect
  vtable slots. They must be corrected alongside the locking fix.
* PuppetState's detach handler keeps a reference to a map value after erasing
  it; an owning Handle must survive through the corrected unregister call.

The revised plan specifies owner-matched lock scopes, conditional use of the
non-locking API, listener lifetime fixes, failure handling and focused native
regressions. It also identifies callback lock-context research still required
before implementation is accepted. A shared SDK change requires all consumers'
Release builds and coherent package provenance.

Runtime validation still requires isolated save-load/new-game/first-save tests,
clothing checks, CET isolation and captured thread stacks if a freeze remains.
Address matches and native regression success do not establish game compatibility.

Changes made by this investigation: research documents and ignored extracts.
No native source, saved patch, lockfile, Git state, game or MO2 file was changed.
