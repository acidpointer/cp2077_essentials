Legacy ABI compatibility: evidence audit
=======================================

Date: 2026-10-24
Scope: shared compatibility for unchanged plugins, not individual DLL patches.
Companion plan: docs/legacy-plugin-compat-plan.txt
Limitations follow-up: docs/legacy-plugin-compat-mitigations.txt
Implementation readiness: docs/legacy-plugin-compat-readiness.txt

Conclusion
----------

Several mechanisms are now demonstrated in isolated laboratory programs.
Others were disproved in the tested configurations or remain unimplemented.
There is no evidence for production-ready, universal compatibility. Research
cannot close gameplay, native-Windows, performance or save-compatibility gaps
without the implementation and the corresponding integration tests.

The current candidate combines versioned entry thunks, explicitly bounded value
marshalling and live protected object views. Shared schemas describe engine/SDK
ABIs, types and operations; plugin names and file hashes are not adaptation keys.

Evidence ledger
---------------

E01. Loader API compatibility does not imply engine ABI compatibility.
Status: established by local source inspection.
Evidence: Api/v1/Sdk.hpp exposes a narrow service table. Relocation-inl.hpp
returns raw addresses to compiled helpers. Scripting/Functions.hpp allocates
sizeof(T) in plugin code. Calls and direct accesses bypass loader services.
Consequence: a call-only shim cannot cover all existing SDK code.

E02. SDK semantic version alone cannot select the historical engine layout.
Status: established for the compared snapshots.
Evidence: both the SDK's pre-2.5 parent and 2.5 base CMakeLists.txt declare
VERSION 1.0.0, despite the function/callback/frame ABI changes. PluginInfo has
sdk/runtime fields but no complete SDK revision or private-layout manifest.
Consequence: use explicit source-runtime ABI families, validate declared
metadata where available, and never infer an ABI solely from sdk=1.0.0.

E03. Query is too late to establish control over all initialization.
Status: established by source, documentation and fixture.
Evidence: PluginSystem::Load invokes LoadLibraryEx before Query. Observed:
  Before LoadLibrary
  DLL static initializer
  DllMain attach
  After LoadLibrary, before Query
  Query reached
Consequence: initialize the compatibility machinery before LoadLibraryEx.
For early engine interactions an ABI family must already be selected; no
generic safe execution of arbitrary Query/DllMain code was demonstrated.

E04. Early module notification exists, with severe callback restrictions.
Status: initially documentation-only; E22 adds positive isolated platform tests.
Evidence: Microsoft's LdrRegisterDllNotification documentation specifies
notification before dynamic linking. Its callback documentation forbids calls
into other modules. The API is also documented as subject to change/removal.
Consequence: if adopted, notification may only publish preallocated module
range records. Decoder work, logging and backend initialization belong outside
the notification callback. Availability and ordering require platform tests.

E05. The game's address list cannot generate a complete adapter automatically.
Status: measured on the installed 2.5 address database, read-only.
  Entries:                                      1,118,540
  Entries carrying a symbol name:                       84
  Unique primary hashes:                        1,032,136
  Duplicate primary-hash groups:                    6,735
  Groups with distinct offsets:                    5,954
  Groups with distinct secondary hashes:           4,237
  Maximum primary-hash multiplicity:                3,578
Fields present: hash, secondary hash, offset, optional symbol.
The database supplies no general function prototypes or object layouts.
Consequence: require reviewed ABI schemas and resolve compatibility entries
with secondary identity/uniqueness checks. Existing loader behavior is not
changed by this audit. Duplicate groups are not evidence that every SDK hash
currently used by the essentials set resolves incorrectly.

E06. RTTI supplies useful, incomplete type evidence.
Status: established by local SDK declarations.
Evidence: IType exposes names/sizes; CClass exposes reflected properties;
CProperty carries a type, parent, offset and flags including inValueHolder.
Core SDK types also contain padding, unknown fields and erased pointers.
Consequence: generate known mappings from headers/RTTI, with explicit semantic
annotations. Allocation sizes and numeric displacements do not identify types.

E07. Old/new fixed callbacks can be bridged with ownership preserved.
Status: isolated Win64 test passed in both environments.
Actual SDK Callback<T,32> and Callback<T,64> have size/handler pairs
0x28/+0x20 and 0x48/+0x40. An adapter retained an old callback in a host owner,
then exercised handler-level copy, move, assignment, invocation and destruction.
Observed: calls=3, copies=2, live payloads after destruction=0.
Limit: this does not prove module-unload safety or every handler/signature.

The initial test also exposed a Clang compile failure when instantiating the
SDK Callback copy constructor: its const source buffer is passed to a void*
helper. The bridge test uses the ABI's handler operations directly. This is
recorded separately; no SDK fix or new patch layer was made here.

E08. Dynamic instruction translation can mediate some unchanged guest code.
Status: restricted Frida Gum test passed in both environments.
A generated DLL contains legacy field reads/writes at +0x10. A host descriptor
maps that field to +0x20. Stalker transformed the executing copy, without
modifying the DLL on disk. Observed first read=42, second read=99, native=99,
three translated accesses. A separate two-thread LOCK XADD test reached exactly
20,000 increments with 20,000 translated operations.
Limits: synthetic layout, explicit host descriptor, selected MOV/XADD operand
forms. No automatic type recovery, full SDK or arbitrary instruction support.

E09. The tested code-cache backend is not exception-transparent.
Status: reproducible failure in the tested Frida configuration.
Explicit RaiseException was caught without tracing. With Stalker enabled the
probe did not complete within 20 seconds, in both system Wine and GE/Steam
Runtime 4. This failure blocks selecting that configuration for production.
Cause within Frida/Wine is not established; this does not prove that every
possible configuration or native-Windows run must fail.

E10. The tested DynamoRIO Windows build failed before fixture main.
Status: reproduced on system Wine, including diagnostic/debug run.
No-client and empty-client runs returned low exit status 5. After correcting
an incomplete extraction, the failure remained. Diagnostic logging showed
the child taking an unhandled execute access violation at 0x179828 before
the fixture printed its main-function output. This was not a fixture assertion.
Limits: no conclusion about native Windows, Linux DynamoRIO controlling Wine,
other DynamoRIO versions, or the underlying injection failure's root cause.

E11. Protected views can mediate accesses at original instruction addresses.
Status: restricted Win64 prototype passed in both environments.
A PAGE_NOACCESS guest view triggers a vectored handler. A predecoded supported
instruction is retried with its RCX memory base mapped to native storage and
the trap flag set. The single-step handler restores the guest RCX. The original
MOV or LOCK XADD executes in hardware; plugin instruction addresses stay intact.
The view remains inaccessible to other threads throughout this process.
Observed:
  fields first=42, second=99; native callback re-entry observed=99;
  ordinary explicit SEH caught; unrelated native access violation caught;
  C++ exception caught with destructor observed;
  two workers: native_count=20,000, total mapped accesses=20,004,
  matching single-step completions=20,004.
The final hardware-SEH fixture used /EHa. An earlier optimized /EHsc variant
failed its added hardware-AV control and is not counted as backend evidence.

Limits: fixed mapping, four-byte MOV and RCX-based XADD only. No pointer-field
conversion, SSE/AVX, REP strings, arbitrary base/index forms, hardware debugger,
interrupted-remap recovery, view reclamation or production engine objects.
The prototype uses bundled Capstone after Gum initialization but no Stalker.
A production handler must avoid allocation, unsafe locks and external decoder
initialization on the fault path. Zydis is a candidate for investigation.

E12. Protected views do not catch every incorrect legacy access.
Status: negative control demonstrated in both environments.
The same guest function received an accessible raw native pointer. It read
the old-offset sentinel 7 instead of the current field 42, with zero view faults.
Consequence: a protected-view backend alone cannot claim process-wide safety.
Every pointer-producing boundary must be covered; raw RVAs, native aliases and
unreviewed hooks need an additional coverage mechanism or remain unsupported.

E13. Fault mediation is expensive on the measured path.
Status: measured once per environment with a matching native fixture baseline.
20,000 increments across two newly created workers:
  System Wine: native 1.484 ms; protected view 85.624 ms.
  GE/Steam Runtime 4: native 0.986 ms; protected view 83.368 ms.
These wall times include worker startup and are not an FPS benchmark or a
general overhead ratio. They rule out assuming that every engine access can
use this path cheaply. Use native identity paths and bounded marshalling where
their contracts permit; measure actual workloads before choosing optimizations.

E14. Complete lifetime, aliasing and hook semantics remain unproved.
Status: implementation/integration evidence required.
Still needed: interior/base pointers, reverse pointer conversion, arrays,
typed bulk copies, weak/strong handles, ABA/reuse, retained async callbacks,
module unload, mixed ABI domains, call-chain ordering and original trampolines.
Function matching does not establish semantic equivalence. Arbitrary patches
inside changed engine functions need more than address translation.

E15. Issue-free game behavior and saves remain unproved.
Status: real implementation and runtime tests required.
No production plugin was admitted by the laboratory code. No game startup,
gameplay, graphics, save/load or save-compatibility test was performed. A native
shim also cannot establish compatibility of changed scripts/resources by itself.

Follow-up evidence (same date, separate laboratory bundle)
---------------------------------------------------------

Entries E16-E21 are in docs/legacy-compat-mitigation-lab/. The original
laboratory bundle and E07-E13 results remain historical observations. This
follow-up ran only system Wine 11.20, not GE/Proton or native Windows. The
guest uses unchanged headers at f9ad5334362a8a0815baf58f47615697485feb52.

E16. Old SDK function creation ignores replacement constructor returns.
Status: actual historical inline implementation exercised in a fixture DLL.
Create allocated 0xC0 and retained that address when a fake constructor returned
a different, larger backing object. The returned guest allocation had stale
parent data. Source: Scripting/Functions.hpp, CClassStaticFunction::Create.
Consequence: preserve the original address or mediate its aliases; changing
the constructor return value alone cannot fix this path.

E17. Precontrolled allocations can be promoted to typed live views.
Status: restricted positive mechanism test.
A fake allocator supplied page-isolated storage. At the typed constructor
boundary the host protected that original address and associated separate
backing. The DLL read old parent/index offsets through the view; the host mapped
them to current offsets and converted parent pointers in both directions.
Null round trips passed. A second same-size allocation remained untyped/writable.
Limits: fake native constructor/storage and two parent identity tokens, three
MOV forms, one thread. No engine registration, native vtable, destruction,
realloc, stack/embedded objects, derived types or production pointer registry.

E18. Unchanged pointer-container layout does not imply safe identity mapping.
Status: source inspection and negative control.
CClass::RegisterFunction appends pointers inline with DynArray::PushBack;
there is no resolved function call at that operation. The actual old PushBack
was given a writable native-format array with spare capacity and a protected
guest function pointer. It stored that guest pointer with zero view faults.
The native host needed the backing pointer. RegisterFunction itself was not
executed in the fixture; its source uses the tested operation.
Consequence: follow pointer-bearing fields/containers when assigning policies,
including types whose own layouts did not change. Test escape in both directions.

E19. Normal SDK execution has useful call boundaries and a stable frame prefix.
Status: source comparison, not an executed frame bridge.
The compared Functions-inl.hpp files are identical: public Execute calls native
engine entry points. The private Execute_ helper constructs a local frame but
is not used by that normal method. Frame fields through +0x63 retain offsets;
new ownership state starts at +0x64. A borrowed-prefix or per-call value policy
is worth investigating. Old frame allocations/copies are not made safe by this.
Pointer values, nested opcode calls and native tail lifetime remain open.

E20. Single-fault MOV mediation reduces a measured cost but remains expensive.
Status: five matched isolated trials, same DLL and parent-pointer read.
20,000 reads, medians: native 0.040 ms; one fault 55.407 ms; two faults 110.843 ms.
The single-fault path updates the exception context and resumes after the MOV;
the comparator retries the MOV with a changed base then handles a single step.
Total checked: 200,007 access violations, 100,000 single steps. This does not
compare directly with E13's threaded atomic workload or predict frame time.
Limits: fixed-order microbenchmark, no concurrency/atomic/debugger tests, no
repeated C++/SEH controls, and no general decoder or instruction emulator.

E21. Allocation promotion does not close raw native alias coverage.
Status: negative control reproduced with the new host.
An accessible native pointer still returned stale parent data with zero extra
faults. E18 additionally shows guest pointers escaping into native containers.
Consequence: the new mechanisms mitigate particular limits; E12's process-wide
coverage problem remains. No general admission or fail-closed claim is justified.

Implementation-readiness follow-up
----------------------------------

Entries E22-E28 use docs/legacy-compat-readiness-lab/, including the separate
system-Wine and GE-Proton runs described below.

E22. Early notification precedes dependency and parent initialization.
Status: passed under system Wine and GE-Proton/Steam Runtime 4.
The readiness platform probe observed notification, C++ initializer and DllMain
in that order for both DLLs, then Query. Its notification callback uses only
preallocated storage and local/inlined operations. This supplies the missing
E04 mechanism test in these environments; native Windows and arbitrary module
dependency/domain selection remain untested.

E23. Compiled typed adapters and a small generated bridge can unwind correctly.
Status: passed under both environments.
Compiled slot adapters preserve a 24-byte aggregate result, mixed integer/double
arguments, nested domains, new-worker routing and C++ cleanup. A generated
sub/call/add/ret bridge with registered unwind metadata passes C++ exceptions,
explicit SEH and a RtlVirtualUnwind model-stack check.
Consequence: start with compiler-built adapters; a full DBI backend is not a
prerequisite for call routing. This does not repair E09/E10 or establish arbitrary
translated-code exception semantics, CFG/CET compatibility or native Windows.

E24. Core layout facts can be extracted from the actual two SDK snapshots.
Status: 11 types and 33 selected fields measured with the Microsoft x64 ABI.
Readiness layout-comparison.json records both sizes/alignments and field offsets.
CClass/CProperty/RefCnt retain sizes; functions, frames and callbacks change.
Representation policies remain UNREVIEWED because pointer contents, lifetime
and virtual-call semantics cannot be inferred from equal field offsets.

E25. Native function constructors publish callbacks before class registration.
Status: established by read-only inspection of the fingerprinted 2.5 executable.
Class, class-static and global constructors store handlers into native tables
and increment a shared counter. Native-only container initialization and class
deleting-destructor allocation size were also inspected. target.json records
identities and reviewed code-range digests without copying game bytes.
Consequence: reserve and initialize persistent adapter ownership before calling
the real constructor. End-of-registration publication is too late as a general
ownership model. A safe game deregistration/rollback contract remains unknown;
the first implementation should retain published registrations for the session.

E26. An old-header registration/invocation chain works with explicit boundaries.
Status: passed in both environments against a fake engine, not CP2077.
Actual old Callback, Create, RegisterFunction/GetFunction, GetParameter and
OpcodeHandlers::Get/Run execute through fake native services and adapted table
entries. The chain retains/releases its callback, separates guest/native class
arrays, maps function/parent pointers, propagates two parameters, nests frame
bindings and cleans up three modeled frames including exception unwinding.
Negative control: a retained metadata mutation stays stale until an explicit
publication barrier. Fake registry detach is supplied by the test, not discovered
in the game. No full native registration transaction or lifetime is proved.

E27. Unload requires atomic admission and retained-owner accounting.
Status: bounded interleaving model, not a runtime concurrency proof.
A separate alive check and active increment has one unsafe schedule among 15;
combined atomic admission has none among 10 modeled schedules. An idle domain
with retained callback slots is still reachable. Reusing a guest address defeats
generation checks when stale raw pointers carry no generation themselves.
Consequence: stable control blocks, coupled admission, owner counts and retained
guest-address tombstones; weak-memory and multithreaded stress remain required.

E28. Native frame ownership and resolved data tables need explicit adapters.
Status: source/executable inspection plus the bounded E26 table/frame fixture.
The game CallNative path constructs/destroys a full native frame. Its destructor
dispatches map cleanup at +0x68. Old frame padding at +0x64 overlaps new state.
OpcodeHandlers resolves to an indexed data table; it is not one function entry.
Consequence: preserve the native-owned tail and use per-domain typed table slots.
The fake frame model does not establish the game's constructor/destructor or
arbitrary opcode argument semantics.

Decision
--------

The mechanisms justify a shared ABI prototype. They do not justify removing
the loader's runtime gate or publishing a compatibility DLL. The most promising
initial design uses cheap typed call adapters and bounded values, with protected
views as a correctness backend for supported changed live objects. Instruction
translation remains an independently gated coverage/performance option.

E22 supplies the E04 Wine/GE mechanism test; native Windows remains open.
Evidence gaps E14-E15 cannot honestly be called closed. E09-E10 identify
failed configurations rather than unexplained compatibility success. E12 is a
demonstrated safety boundary that the implementation plan must address.
The E22-E28 sources, reproduction commands, results and checksums are preserved
in docs/legacy-compat-readiness-lab/. The readiness report separates decisions
that can now be implemented from G1-G5 integration/coverage/performance gates.
